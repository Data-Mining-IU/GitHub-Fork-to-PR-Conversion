\section{Modeling}

This phase implements CRISP-DM Stage 4 using the prepared integrated datasets in \texttt{src/data/modeling\_dataset\_obs30d.parquet} and \texttt{src/data/modeling\_dataset\_obs90d.parquet}. The 30-day export is used as the main modeling table, following the Stage~3 sensitivity recommendation, and the 90-day export is used as a label-window robustness check.

\subsection{Select Modeling Technique}

\subsubsection{Modeling Objectives}

Two predictive tasks are modeled:
\begin{itemize}
    \item \textbf{Classification:} predict whether a repository-season has at least one converted fork (\texttt{has\_conversion}).
    \item \textbf{Regression:} predict the conversion intensity (\texttt{fork\_conversion\_rate}).
\end{itemize}

This dual formulation supports both operational triage (high vs.\ low conversion potential) and continuous forecasting of conversion magnitude.

\subsubsection{Chosen Techniques}

The modeling stage compares baseline and non-baseline methods:
\begin{itemize}
    \item \textbf{Naive baselines}
    \begin{itemize}
        \item Classification: majority-class predictor.
        \item Regression: mean conversion-rate predictor.
    \end{itemize}
    \item \textbf{Logistic Regression} for interpretable linear decision boundaries under class imbalance.
    \item \textbf{Random Forest} and \textbf{Extra Trees} for non-linear interactions and robustness on skewed activity signals.
    \item \textbf{Gradient Boosting} and \textbf{Histogram Gradient Boosting} as additional non-linear ensemble benchmarks for tabular activity data.
\end{itemize}

\subsection{Generate Test Design}

\subsubsection{Validation Protocol}

\begin{itemize}
    \item Hold-out split: 80\% training / 20\% test.
    \item Random seed fixed at 42 for reproducibility.
    \item Classification split stratified by \texttt{has\_conversion}.
\end{itemize}

\subsubsection{Feature and Target Setup}

\begin{itemize}
    \item Input features are restricted to the Stage~3 selected activity features: \texttt{season}, engineered \texttt{log1p\_*} signals, raw activity counts, winsorized activity counts, \texttt{activity\_strength}, and \texttt{stratum\_activity\_quintile}.
    \item Label-derived counters are not used as predictors. In particular, \texttt{n\_forks}, \texttt{n\_converted\_forks}, \texttt{n\_pr\_events}, and \texttt{stratum\_fork\_quintile} are excluded from the feature matrix.
    \item Numerical features are median-imputed and scaled for linear models.
    \item Categorical features are imputed with mode and one-hot encoded.
\end{itemize}

\subsubsection{Evaluation Metrics}

\paragraph{Classification}
\begin{itemize}
    \item Accuracy
    \item Macro-F1 (primary for imbalance-aware quality)
    \item Precision
    \item ROC-AUC (where probability outputs are available)
\end{itemize}

\paragraph{Regression}
\begin{itemize}
    \item Mean Absolute Error (MAE)
    \item $R^2$
    \item Predictions are clipped to $[0, 1]$ before evaluation because \texttt{fork\_conversion\_rate} is a bounded rate by construction.
\end{itemize}

\paragraph{Ranking quality}
\begin{itemize}
    \item Precision@10\%
    \item Lift@10\%
    \item NDCG@10\%
\end{itemize}

\subsection{Build Model}

\subsubsection{Implementation}

All models are implemented in \texttt{scikit-learn} pipelines in \texttt{src/Modeling.ipynb}:
\begin{itemize}
    \item shared preprocessing through \texttt{ColumnTransformer};
    \item model fitting on train split only;
    \item test predictions and metric computation on held-out data.
\end{itemize}

The following trained models are compared:
\begin{itemize}
    \item Classification: baseline, Logistic Regression, Random Forest Classifier, Extra Trees Classifier, Gradient Boosting Classifier, Histogram Gradient Boosting Classifier.
    \item Regression: baseline mean, Linear Regression, Random Forest Regressor, Extra Trees Regressor, Histogram Gradient Boosting Regressor.
\end{itemize}

\subsubsection{Hyperparameter Tuning}

Compact hyperparameter tuning is implemented with \texttt{RandomizedSearchCV}:
\begin{itemize}
    \item \textbf{Classification:} tuned Random Forest with macro-F1 objective.
    \item \textbf{Regression:} tuned Random Forest with MAE objective.
\end{itemize}
The tuned models are compared to untuned baselines on the held-out test set.

\subsection{Assess Model}

\subsubsection{Assessment Against Success Criteria}

The notebook directly checks whether:
\begin{itemize}
    \item Classification models outperform the majority baseline on Macro-F1.
    \item Regression models reduce MAE versus the mean baseline.
    \item Regression models achieve non-negative and preferably positive $R^2$ on the test set.
\end{itemize}

These checks align with the data mining success criteria defined in the business understanding stage.

\subsubsection{Actionable Segment Analysis}

The most actionable segment is therefore the \textbf{top-ranked 10\% repository-seasons}. This segment contains 2,000 test observations, 1,895 observed conversions, and a lift of 2.01 over random selection. If the operational goal is to prioritize repositories for maintainer outreach, onboarding guidance, or deeper qualitative review, this top decile is the clearest target group.

The second and third deciles remain useful but weaker: D2 has 87.45\% precision and D3 has 76.75\% precision. After D5 the ranking drops below the global conversion rate, so the lower deciles are not attractive for proactive intervention. This creates a practical segmentation rule: focus first on D1, optionally expand to D2--D3 if capacity allows, and avoid treating the full population as equally promising.

\subsubsection{Validation Stability (Time-Based Folds)}

\textbf{What a ``fold'' means here.} The modeling table is keyed by \texttt{season} with two values (\texttt{winter\_spring} and \texttt{summer\_autumn}). A time-based fold trains on one season and tests on the other. Because there are exactly two seasons, we evaluate \textbf{two folds}:
\begin{itemize}
    \item Fold A: train \texttt{winter\_spring} $\rightarrow$ test \texttt{summer\_autumn}
    \item Fold B: train \texttt{summer\_autumn} $\rightarrow$ test \texttt{winter\_spring}
\end{itemize}

\textbf{How this maps to the success criterion.} The criterion compares the \textbf{best vs worst fold} for each metric (not random hold-out vs a single temporal split). For higher-is-better metrics we report relative gap $(\text{best}-\text{worst})/\text{best}$; for MAE (lower is better) we report $(\text{worst}-\text{best})/\text{best}$.

\subsubsection{Practical Interpretation}

\begin{itemize}
    \item Tree ensembles provide flexible non-linear modeling for heavy-tailed repository activity.
    \item Logistic/linear models provide a transparent baseline for communication to non-technical stakeholders.
    \item Baseline comparisons prevent over-claiming improvements in an imbalanced, noisy environment.
\end{itemize}

\subsubsection{Limitations}

\begin{itemize}
    \item Time-based validation uses two seasonal folds (both train/test directions). This matches the ``best vs worst fold'' wording, but still provides only two temporal regimes; richer multi-fold checks require exporting additional time slices.
    \item 30d-vs-90d sensitivity checks label-window robustness, but it does not replace a business decision about which conversion horizon is operationally preferred.
    \item Target construction remains based on heuristic fork-to-PR matching and may contain residual label noise.
    \item Extreme conversion ratios in low-fork repositories can still challenge regression stability.
\end{itemize}

\subsubsection{Hyperparameter Tuning Outcome}

Randomized search is run before final assessment for Random Forest models.
\begin{itemize}
    \item Tuned RF \textbf{classification}: optimized with macro-F1 objective.
    \item Tuned RF \textbf{regression}: optimized with negative MAE objective.
\end{itemize}

Interpretation:
\begin{itemize}
    \item Tuned and untuned variants are both included in the downstream validation tables.
    \item The selected best model is therefore chosen after, not before, hyperparameter tuning.
\end{itemize}
